## 2. プロジェクトの目的と現在地

最終目的は大腿骨全長（FL）の測定である。Stage2〜4で超音波動画からpseudo-3D教師点群を構築し、
Stage5ではPointNeXt-Sによる点単位segmentationを開発してきた。Stage6は未着手。
現行のpseudo-3Dを物理的に正しい3D形状と仮定しない。

S5-15は回転augmentation短期比較後にR0（回転なし）を維持し、新規50 epoch runを終了した。
validationではbest epoch6からlast epoch50へF1が9.28%から5.00%、recallが38.95%から6.97%、
TP0が1/18から10/18へ悪化した。一方train sanity recallは62.33%から97.36%へ上昇した。
汎化不足と整合するが原因は未確定。100〜200 epoch延長・production採用は行わない。

後続順序は、S5-17幾何診断 → S5-18 CE/Dice比較 → S5-19動画context比較 →
S5-20のtask・座標契約再設計と最終評価である。S5-19はS5-17の結果によらず実施する方針。
S5-17は、segmentationと後処理でFLに必要な情報を扱えるか、どの幾何表現を後続へ渡すかを調べる。
**学習可能性やgeometry headの汎化性能をtraining-free診断だけで証明しない。**

## 4. 旧設計から必ず訂正する前提

### 4.1 H17-1と採否規則

**既存のアノテーション済み180動画に臨床実測FLはない。** 手元でFLと呼んでいた値は
BBoxアノテーション由来で、既存スクリプトの`femur_traj_len`は正規化された2D重心のframe間移動距離の和である。
骨長やmm単位の実測FLではない。この値を臨床正解へ改名して使わない。

旧10.1の「train_coreで臨床FL誤差が最小の代理FLを選ぶ」というH17-1・採否規則は実行不能である。
全件を臨床FL欠損として除外して完了扱いにすることも認めない。
GTから作った量を別のGT由来量へ近づけても、臨床的な正しさの検証にはならない。

**最初の報告でH17-1の改訂案と採否規則を提出する。**
検討方向は、GT表現の情報保持・幾何的整合性・摂動への安定性と、予測由来幾何のGT由来幾何への一致を分離すること。
これは方向性であり、具体的な参照量・閾値・候補選定規則は未採用。
外部的な正しさを判定できない場合には「判定不能」を許容し、無理に1案を選ばない。
旧「T_FL以内の動画が過半」という規則の何を維持・修正するかも、実データ結果を見る前に管理へ返す。

### 4.2 mmと座標

mm/pixelは元frame基準。`pixel_xy`はlocal crop座標であり、crop/resize逆変換後にx/y別スケールを適用する。
監査したspacingは144/144が既定値1.0/1.0と一致し、実mm/pixelを確証できない（UNCONFIRMED）。
全H5の全項目にmm情報がないと証明したわけではない。1.0を実測値として採用しない。

供給元、保存形式・単位、完全一致の動画キー、動画内一定かframe別か、frame対応を確定する。
異方的スケールを含む往復変換を合成テストし、許容誤差を実行前に固定する。
pseudo-3DのZは物理mmと未確認であり、xyだけの換算から3D長をmmと呼ばない。
pixel／正規化量／mmを型・メタ情報・出力で区別し、未換算を0や他動画の値で埋めない。
`T_FL`はユーザー設定事項で、推定・既定値の捏造をしない。

### 4.3 同一検査と5例

D-041により同一検査の複数動画が存在するが、抽選単位はファイルのまま維持した。
**旧train162とvalidation18にまたがる同一検査は4グループで、所属ファイルは両集合の合計17件。validation側の正確な件数は未確認（既存記録上の範囲は4〜13件）**。
別sweepの外観が異なるという説明は、統計的独立やバイアスの小ささの実証ではない。
動画数を独立検査数と同一視せず、結論にこの限界を付ける。分割を変更しない。

別の**実測FL付き5例**は各例に複数動画があり、S5-18学習中にアノテーションする方針（D-040）。
同一被験者の医師計測値だが、左右・測定撮影時期の対応は未確認。
固定した方法による探索的比較・mm換算の健全性確認を補助する用途に限る。
**S5-17の方式選択・較正・学習・採否に使わない。検査内一貫性の比較も例外ではない。**
今回の入力には含めず、比較単位等を後続へ持ち越す。5例を独立外部test完成と扱わない。

## 5. 入力と封印・共有の境界

- GT幾何・priorの構築はtrain_core。予測診断は既存R0 best epoch6を主、last epoch50を補助としてvalidationで行う計画。
  実在する保存予測の所在・run/epoch・全点対応・prob有無を監査してから対象を固定する。
  train_coreの旧予測を使う提案はin-sample診断と明示し、validationと分ける。
- 旧予測保存物がsanity3＋validation18だけを覆う可能性を考慮し、train_core144の予測があると仮定しない。
  不足をGPU再推論や別checkpointへの無断切替で埋めない。
- 旧checkpointはinternal_testを学習済み。S5-20cでもその18件への評価は禁止。
- 新CLIでもpinから契約を解決し、**GT・予測・中間H5・対応表等のデータ読込前**に対象集合を確認する。
  guardだけでなく、処理目的に応じたtrain_core／validationの許可リストとの照合も行う。
  直接identityが読めない保存物はcoverageで対応を確定し、不明なものは停止。directory-modeへのfallbackをしない。
- identityはtimestamp形式の全trailing数値（第4セグメントを含む）とcase形式に対応する既存実装を使う。
  独自正規表現や先頭部分一致で別動画を併合しない。
- 封印リスト、GT統計、層化中間結果・セル別配分を開いて仕様決定しない。旧180と新162の統計差から封印側を推定しない。
- 実ID・パス・動画別座標／端点／長さ・結果・患者画像・対応表はprivate。共有は承認した匿名集計・照合情報のみ。
  stdout、例外、traceback、一時ファイル、図も同じ境界を守る。
- `export_anonymized_stage5_metrics.py`、`check_stage5_effective_run_config.py`、
  S5-15 P1 manifest auditは未guardのため封印期間は使用禁止。
  既存privacy self-checkの命名対応不足を引き継がず、新経路の共有テストを実装する。

## 6. 候補と共通評価器の具体化

旧10.1の候補は(a)frame軸平行BBox、(b)oriented box、(c)頑健な主軸端点、
(d)最良frame＋端点、(e)単位制約付きpseudo-3D軸である。
後処理はなし／最大連結成分／frame間持続性／確率上位、prior-onlyはtrain_core由来を検討する。
これらは無制限な総当たり探索の承認ではない。候補数・組合せ・閾値・比較順序を事前提案する。

予定構成は`Stage5/stage5/geometry/`のnumpyのみ・torch非依存の幾何コアと、
`Stage5/evaluate_stage5_geometry.py/.sh`、`Stage5/checks/dummy/check_dummy_geometry_*`。
H5 I/OはCLI側に分離する。新しいmodel/head/lossやStage6本実装は今回の対象外。

最初に具体化する事項:

1. `FrameGeometry`（frame、存在、複数instance、中心・軸・長さ・幅・端点・点数）と
   `VideoFLEstimate`（推定値・単位・使用frame・失敗理由等）、`PixelToMM`の契約。
   「信頼度」を置く場合は定義し、未較正のscoreを正解確率と呼ばない。
2. GT／予測の点数・点順・frame・座標の一致検査、valid/ignore、空GT・空予測、退化PCA、
   軸の符号・端点交換、複数領域のinstance選択／matching、失敗時の分母と集計。
3. 最良frame選択と後処理が予測側で利用できる情報。GTを使うoracle診断は明確に分離し、実用性能に混ぜない。
4. prior-onlyの座標系、平均の定義、train_coreだけからの構築、対象自身の寄与を含む場合の扱い。
5. GT近傍・ignore・遠方FPの定義。距離だけで「別の解剖構造」と断定しない。
6. 幾何誤差・存在判定・頑健性の指標と単位。mm未確定時の診断を提案するなら、mm評価・臨床妥当性から分離する。
   臨床FLがない集合で臨床MAEや一致限界を作らない。
7. H17-1〜H17-5の変更／維持／保留、採否基準、判定不能時の後続への渡し方。

既存の再利用候補:
`stage5/utils/{split_contract,split_identity,file_list_mode,h5_io}.py`、
`checks/real_h5/check_stage5_{gt_component_count,xy_coordinate_provenance,coordinate_transform_reconciliation,s5_14_supplement}.py`。
単に既存checkerを呼べば封印対応済みとは扱わず、計算関数とCLIの安全な経路を分けて調べる。

## 7. 最初に行う作業と承認境界

**現在着手できること:** リポジトリ内の仕様・コード・保存形式の読取り、既存部品の再利用調査、
具体仕様案・変更ファイル案・合成テスト案・実機入力監査手順の作成。
この範囲で小さな確認ごとに管理判断を求めず、まとまった初回報告を提出する。

**現時点では実データを走査して候補を比較しない。** mm供給元や予測ファイルの実機所在が不明なら、
必要な項目・対象・読み取り範囲を具体化し、個人情報を含まない所在確認を依頼する。
管理チャットへ返す初回報告で、改訂H17-1・採否規則・実施範囲の判断を受ける。
これは旧H17-1の前提崩れと未確定の実施条件による境界であり、Step 0の再承認ではない。

仕様確定後は、実装 → 合成テスト → 結果報告 → 実機fail-fast → 限定CPU診断 → 管理受入の順。
旧方針のCPU量上限は本実行1回、不具合修正後の再実行1回までを基本として具体計画へ落とす。
入力監査の読取り量・本実行との重複も明示し、結果を見ながら条件を変えて繰り返さない。
学習・GPU・再推論・production変更・封印解除は対象外。

合成テストは意味のある成功・失敗経路を含める。変換往復、異方的スケール、既知形状、退化・空集合、
点対応不一致、複数instance、guardの読込前拒否、出力境界を検証する。
本番pinsや実データに依存せず、合成契約を使用する。文字列検査や拒否ケースだけで成功経路を未検証にしない。
