## 全体管理・共通資料

- `stage5_revision_management_record.md`: authoritative Stage 5 overview,
  chronological revision record, accepted decisions, current status, and next
  implementation order. Start here when deciding what work comes next.
- `s5-08-09/stage5_overlap_aggregation_handoff_prompt.md`: historical S5-08/09 teacher v6 overlap aggregation and BatchNorm parity specification. Use the revision management record for current priorities.
- `s5-08-09/stage5_overlap_aggregation_implementation_policy.md`: implementation-chat
  rationale behind the handoff prompt's overlap aggregation checker design
  (module reuse, accumulator math, mean baseline parity method, output
  layout, and the F1-F3 design decisions). The handoff prompt is authoritative
  if the two disagree.
- `stage5_pointnext_s_training_evaluation_report.md`:
  authoritative investigation history and current findings.
- `data_construct.md`: layout of an evaluation output directory
  (`stage5_evaluations/<EX_DATE>/<EXPERIMENT_NAME>/`) -- per-checkpoint
  predictions/PLY/metrics, `prediction_frames/`, the anonymized-metrics export,
  and the share / DO_NOT_SHARE boundary. Read it before copying anything out of
  an evaluation directory.
- `TRAINING_IMPROVEMENT_PLAN.md`: earlier planning history; use the evaluation
  report for detailed evidence and `stage5_revision_management_record.md` for
  the current priority order.
- `stage5_edit_prompt.md`: historical record of the move from the interim
  segmentor to the official PointNeXt-S structure. Background only.

## Core code

Paths below are relative to `Stage5/` (this file lives in `docs/stage5/`).

- `train_stage5.py`: training CLI.
- `infer_stage5.py`: inference CLI.
- `evaluate_stage5.py`: annotated H5 evaluation CLI with window and aggregated metrics.
- `prepare_stage5_evaluation_data.py`: selects evaluation H5 files and collects reference PLY files.
- `summarize_stage5_evaluations.py`: combines metrics from multiple checkpoints.
- `export_anonymized_stage5_metrics.py`: creates shareable split-labeled metrics and a separate private ID map.
- `export_stage5_prediction_frames.py`: S5-15 CLI that renders an existing evaluation's predicted-positive vs GT segmentation onto the original local-crop frame images, so that false positives can be identified as anatomy, instruments or artifacts instead of being read off a PLY. Inputs are existing artifacts only -- the saved per-video `predictions/*.npz`, the annotated teacher H5, and the intermediate pseudo3d H5's `local_encoder_images` (the image space `pixel_xy` is expressed in, per the S5-14 Step H2.5 provenance audit). No training, no inference, no CUDA, and nothing under the evaluation directory is modified: output goes to a new `prediction_frames/` subdirectory of the per-checkpoint evaluation directory (see `data_construct.md`). The intermediate H5 is located with the S5-14 audit's `resolve_intermediate_h5()`, imported rather than copied, and the resolution method (recorded attr vs. basename fallback) is recorded per video and never conflated. A video whose intermediate H5 or dimensions cannot be resolved is reported as un-visualizable rather than borrowing another video's dimensions; a prediction/H5 point-count mismatch, out-of-range `pixel_xy`, or a `frame_order` beyond the available images stops the run instead of being skipped. Frames are selected by false-positive count descending with `frame_order` ascending as the tie-break (all-frames output exists but is not the default, since 21 videos x all frames is thousands of unreadable PNGs). **The output is DO_NOT_SHARE**: it contains rendered patient frames, and file names/CSVs/manifest carry real video names.
- `stage5/`: dataset, model wrappers, losses, metrics, and utilities.
- `stage5/utils/file_list_mode.py`: S5-15 fixed train/val file-list inputs (stdlib only). Validates a saved list pair -- both lists present and readable, non-empty, no duplicates within a list, no train/val overlap, no repeated file name across the union (one video name = one identity for angles and evaluation), every entry existing and matching the teacher pattern, and an optional exact total -- then writes the combined train-then-val manifest that `train_stage5.sh`'s teacher preflight inspects, so the preflight and the training run can never see different file sets. Every failure raises/exits 2 instead of falling back to directory splitting, which is the silent-different-split failure the mode exists to prevent. Also provides `compare_file_lists()`, which separates a genuine content difference (different videos, or a different order) from a mere path-representation difference (same videos under another mount prefix), reporting both `content_sha256` and `identity_sha256` rather than relaxing the comparison until it passes.
- `stage5/utils/split_contract.py`: S5-16 Step 0 B' seal contract (stdlib only, no numpy/h5py/torch, and it runs before any H5 is opened). Keeps three things deliberately apart. (1) The **seal registry** is the single authority for which videos are sealed; it is resolved independently of whichever split manifest is in use and its deny is evaluated **before** any manifest's allow, so no manifest -- legacy included -- can erase, replace or shrink it. A manifest's own `sealed_splits` is a separate matter -- the splits *that manifest* defines as sealed sets -- and the two are not conflated: a legacy manifest defines none, because its 162-video train list is not the 18 sealed videos. Every manifest must still set `seal_registry_required`, so an absent or empty seal field is never read as "nothing is sealed"; and a manifest that does claim to hold the sealed split is checked against the registry's `sealed_list_identity_sha256`, since declaring a split's name proves nothing. (2) The **pins** file (`stage5/config/split_contract_pins.json`, git-tracked) fixes what each contract artifact's SHA-256 must be; a hash an artifact states about itself is never used as the expected value, because an artifact and its self-stated hash can be changed together. `--split_manifest`/`$STAGE5_SPLIT_MANIFEST` therefore names an **approved pin, not a path**, so a run cannot be aimed at an arbitrary file and an unapproved manifest has no name to give. A missing or unapproved selection **stops the run**; it never means "unrestricted". (3) **Bootstrap** is the one narrow path that creates the registry in the first place -- requiring a registry to read the inputs that produce the registry would deadlock -- and it closes permanently once a registry exists or is approved, so it can never overwrite or regenerate a confirmed split. Also provides `load_input_audit()`/`verify_bootstrap_inputs()`, which check each initial-build input against the hash the S0-1 audit fixed for it -- the expected value has to arrive from the audit record, because a hash recomputed from an input and compared with itself always matches and verifies nothing; `verify_intermediate_fingerprint()`, which checks the dry run's own output file against the fingerprint fixed at that time, catching an intermediate whose GT classification or FL groups were altered while its input list, candidate set and seed stayed the same; `verify_split_partition()` (the six checks a new split must pass: mutual disjointness, 144/18/18, train_core+internal_test reconstructing the old train list, the union covering the old video set, train-sanity staying in train_core, and validation unchanged in content *and* order), the legacy-manifest writer, and the `assert` CLI that `train_stage5.sh` calls before its preflight. Refusal messages carry positions and counts only: a real path or file name would itself be a private identifier.
- `stage5/utils/split_identity.py`: S5-16 Step 0 video-identity resolution for the seal contract (stdlib only). The seal is enforced per **video**, not per path, because the same video appears as a teacher H5, an intermediate pseudo-3D H5, a prediction NPZ, a GT-region JSON and rows in several CSVs; a guard matching one spelling of one of those would not be a guard. Identities are read from the file name by a fixed `YYYYMMDD_HHMMSS_N` pattern (with lookaround, so a longer digit run cannot yield a shifted false match). **A name that yields no identity is not evidence that the artifact is free of sealed videos**: shared-name JSON/CSV outputs, multi-video aggregates and alias-only artifacts must be covered by an `ArtifactCoverage` record bound to that artifact's own content hash, or the read stops. A coverage record whose hash no longer matches, or that lists no videos, is refused rather than treated as an all-clear -- one artifact's record is never reused to vouch for another.
- `stage5/utils/split_allocation.py`: S5-16 Step 0 deterministic half of the B' split (stdlib only). The second stratification axis is **not** a clinical FL tertile: the 180 annotated videos have no clinical measurement, and the FL figures that exist are derived from the BBox annotations, so D-039 replaced that axis with `gt_positive_frame_count` -- the number of distinct frames holding at least one valid GT-positive point in the saved teacher point cloud. That quantity is **not a femur length, not a size and not an observation time** (fps and stride are unconfirmed across the 159 candidates, so a slow sweep over a short femur and a fast sweep over a long one are not distinguished), and it balances only the draw of internal_test 18 out of the 159 candidates -- validation 18 is fixed and train_core 144 carries the fixed sanity 3, so it is not a balance "across the three splits". A genuine zero is a value and is ranked with the rest; only a value that cannot be computed stops the build, and there is no missing group. `assert_stratification_is_constructible()` requires **strictly increasing group medians**, because the rank split will happily produce three groups when every value is identical -- it is a pre-fixed guard against degeneracy and is documented as guaranteeing neither disjoint group ranges nor an effective stratification, with `count_boundary_tie_members()` recording how many candidates sit in a value shared across a boundary. `assert_supported_versions()` refuses a spec version the implementation does not know, **including when the corresponding CLI argument was omitted**. The remainder rule, tie-break by saved list order, largest-remainder allocation with capacity, and the **SHA-256 keyed sort** draw (`SELECTION_METHOD`, fixed clause by clause so the draw reproduces from a written specification) are unchanged from the FL-era design.
- `stage5/utils/class_weights.py`: S5-16 Step 0 home of `compute_class_counts_from_h5()` and `pointnext_class_weights_from_counts()`, moved **byte-identically** out of `train_stage5.py` (same formula, same `epsilon=0.02`, same mean-1 normalization, same float32 cast). The move exists so the train_core-only recomputation can run on CPU without importing torch, and so one implementation serves both the training run and the Step 0 tool -- a second copy of the formula is how two "identical" computations stop being identical. Counting reads each video's original H5 once and uses valid, non-ignore points only; it deliberately does not go through the overlap windows, which would count points in the overlap twice.
- `stage5/utils/train_sanity_selection.py`: S5-16 Step 0 stdlib-only reference copy of the train-sanity selection. `evaluate_stage5.py` and `prepare_stage5_evaluation_data.py` each keep their own copy (identical apart from a temporary variable) and are deliberately left alone, since changing the evaluation path is not part of Step 0; this copy exists so the S0-1 audit can re-derive the selection without importing torch or h5py, and `check_dummy_step0_input_audit.py` extracts the `evaluate_stage5.py` copy by text and asserts the two agree, the same anti-drift trick `check_dummy_fixed_list_mode.sh` uses on `train_stage5.sh`. The reason this matters for Step 0: the draw takes from the list **in order**, so the identity of the three sanity videos is defined only relative to the saved train162 list, and re-running it against train_core would pick different videos.
- `stage5/config/split_contract_pins.json`: the git-tracked approval record for the seal registry and split manifests. Changing a pin is a diff the user reviews and commits, which is the approval step. An empty `pins` is the pre-Step-0 state: normal training/evaluation/inference all refuse to start, and only the explicitly requested initial build may run. The known limit is written into the file rather than implied -- the same user can edit both a pin and the artifact it pins, so this prevents misdirection and unapproved substitution, not a determined operator, and no signing infrastructure is introduced.
- `stage5/utils/prediction_frame_render.py`: S5-15 rendering core for `export_stage5_prediction_frames.py` (numpy + cv2, no torch). The six-way classification is not reimplemented here: it calls `visualization_export.diagnostic_segmentation_categories()`, the same function the diagnostic PLY writer uses, so the PNG and the PLY cannot disagree about what a point is, and it uses that module's `DIAGNOSTIC_CATEGORY_COLORS` for the same reason. The existing Stage 4 `render_point_labels` could not be reused because it is fixed to three labels, so its drawing method is followed instead (integer-rounded coordinates, a dilated marker per category, alpha blending). `false_positive` is drawn last so it is never hidden by another category, and `true_negative`/`ignore_other` are off by default because they fill the frame. `frame_point_index_ranges()` groups points by frame with the same stable argsort/bincount method as the Stage 4 exporter. `load_image_to_uint8_gray()` imports Stage2to4's converter lazily, by call, so `sys.path` is manipulated only in the CLI and this module stays importable without Stage2to4; it raises rather than substituting a local reimplementation, because a different grayscale conversion would make this export incomparable with the Stage 4 GT visualization.
- `stage5/utils/rotation_augmentation.py`: S5-15 training-only random Z-rotation augmentation (pure numpy, no torch). The angle for one (video, epoch) is derived deterministically from `(base_seed, epoch, stable_video_id)` via SHA-256 (never Python's `hash()`, which is randomized per process and so would differ between DataLoader workers) seeding a local `numpy` `Generator`, so every window of a video shares one angle within an epoch regardless of worker count or fetch order, and numpy's global RNG (used for shuffling/model init) is never consumed. `stable_video_id_from_path()` uses the file name alone so a different mount prefix or a relative path cannot change the angle. `AugmentationConfig.resolve()` records a concrete `base_seed` (explicit value wins; otherwise `train_seed + 500000`) plus the `seed_source` and the derivation formula for config.json/checkpoints, never a null seed. `rotate_video_points()` returns the input array itself with a `None` angle when the mode is `none`, keeping the disabled path free of any angle derivation. The rotation-matrix convention is bit-identical to the S5-14 supplement-2 coordinate diagnosis (right-handed CCW about +Z, float64 internally, float32 out) so the ±15° range carries the same meaning; that finished S5-14 checker is neither imported by nor modified for this module.
- `train_stage5.sh`: editable training launcher with external data paths. Setting both `TRAIN_LIST` and `VAL_LIST` switches it to S5-15 fixed-list mode: `--train_list`/`--val_list` are passed, `--train_dir` and `--val_fraction` are not (so the seed-based re-split is unreachable), truncation is disabled, `INPUT_DIR` is never scanned, and the teacher preflight inspects the listed files themselves. Setting only one is an error with no fallback. Leaving both unset keeps the historical directory-scan behavior unchanged. **S5-16 Step 0 adds the seal contract**: `SPLIT_MANIFEST` (an approved pin name, not a path) is checked by `stage5/utils/split_contract.py` **before the teacher preflight**, because that preflight opens every listed H5 and a guard placed after it would be reading sealed videos to decide whether it may read them; a directory-scan run is refused outright unless the contract permits directory mode, since a glob has no ordered contract to check against. The fixed-list manifest is now written to `PRIVATE_WORK_DIR` instead of `/tmp` (it holds real H5 paths) and is removed by the existing `trap ... EXIT` on normal and abnormal exit alike. The teacher preflight's **set-dependent** expectations can come from a pinned private file (`TEACHER_EXPECTED_JSON`) instead of the in-script literals, and `EMIT_TEACHER_EXPECTED` writes the observed totals for a new target set once; the set-independent checks (teacher version, `valid_mask` vs `point_label != -1`, provenance, required datasets) are unchanged. Its QC totals are withheld from shared output **on success and on failure alike** -- the 180-file constants are already in git, so publishing the 162-file numbers would give the sealed videos' totals by subtraction -- and the numbers needed to diagnose a mismatch go to `PREFLIGHT_PRIVATE_LOG`. `AUGMENTATION`/`AUGMENTATION_ROTATION_DEGREES`/`AUGMENTATION_SEED` select the S5-15 training-only rotation, defaulting to `none`.
- `infer_stage5.sh`: editable inference launcher with external data paths.
- `evaluate_stage5.sh`: fixed train-sanity/full-validation checkpoint evaluation pipeline.
- `export_anonymized_stage5_metrics.sh`: standalone anonymized-metrics exporter for an existing evaluation.
- `export_stage5_prediction_frames.sh`: launcher for the S5-15 prediction frame visualization. Defaults to the S5-15 R0 50-epoch evaluation output and runs `best` (epoch 6) and `last` (epoch 50) over both `train_sanity` and `validation` with an identical layout, so the same video and frame number can be compared side by side across the two checkpoints. `DRY_RUN=1` resolves every input and writes the CSVs/manifest without rendering, which is the intended first step on real data. No GPU environment variables: the export is CPU-only.

## Check and debug scripts

`check_*.py` and `check_*.sh` are smoke tests or visualization helpers. They are
grouped under `checks/` so they stay separate from the regular training and
inference launchers.

Main groups:

- `checks/dummy/check_dummy_*`: synthetic H5/model checks.
- `checks/visualization/check_window_batch_ply_export.*`: frame-window DataLoader PLY export.
- `checks/s3dis/check_s3dis_*`: official PointNeXt/S3DIS checkpoint and data checks.
- `checks/transfer/check_s3dis_to_stage5_pointnext_s_transfer.*`: partial S3DIS-to-Stage5 weight transfer.
- `checks/real_h5/check_real_h5_pointnext_s_transfer_forward.*`: real Stage5 H5 forward/PLY check.
- `checks/real_h5/check_stage5_batch_integrity.*`: Dataset/window/point_indices audit against source H5 (S5-04).
- `checks/real_h5/check_stage5_padding_parity.*`: zero-padding sensitivity for logits/gradient/BatchNorm (S5-05).
- `checks/real_h5/check_stage5_overlap_aggregation.*`: overlap-window probability/aggregation comparison (S5-08, 実装事項A).
- `checks/real_h5/check_stage5_batchnorm_mode_parity.*`: eval()/train() BatchNorm probability parity (S5-09, 実装事項B).
- `checks/real_h5/check_stage5_batchnorm_recalibration.*`: diagnostic BatchNorm running-statistics recalibration from the training split, compared against the original checkpoint (S5-10). Saves a diagnostic checkpoint under `stage5_debug/`; never overwrites the original and is never shared.
- `checks/dummy/check_dummy_pointnext_s_groupnorm.*`: BatchNorm-default backward-compatibility and GroupNorm structural/train-eval-parity checks for the PointNeXt-S wrapper's `pointnext_norm` option (S5-11). `--self_test` is CPU-only; the full run needs CUDA and dummy H5 data only.
- `checks/transfer/check_stage5_batchnorm_to_groupnorm_transfer.*`: transfers the existing Stage5 BatchNorm S3DIS partial-init checkpoint's trainable parameters (conv/linear/head/norm affine) into a freshly constructed GroupNorm model, excluding only BatchNorm running buffers (S5-11). Saves `stage5_pointnext_s_s3dis_partial_init_groupnorm.pt` alongside the existing BatchNorm partial-init checkpoint.
- `checks/dummy/check_dummy_label_policy.*`: synthetic BBox non-contour label-policy tests -- pure-array geometry/no-op/fail-fast tests plus a Dataset-level integration test on a hand-built H5 (S5-12, Step E2). No CUDA needed.
- `checks/real_h5/check_stage5_label_policy_bbox_preflight.*`: audits every teacher v6 H5 in the train/val lists for the BBox non-contour label-policy contract (every ignore point lies inside a stored BBox) before enabling `--label_policy bbox_noncontour_background` (S5-12, Step E3). CPU/h5py only.
- `checks/real_h5/check_stage5_label_policy_dataset_parity.*`: confirms on real teacher v6 H5s that switching `--label_policy` changes only labels/valid_mask at audited target points, with everything else (points/features/frame_order/point_indices/window bounds) identical (S5-12, Step E4). CPU/h5py only.
- `checks/real_h5/check_stage5_label_policy_ablation_eval.*`: evaluates one Run A/B label-policy checkpoint against three common targets (`canonical_v6` with a mean-baseline parity gate against plain `evaluate_stage5.py`, `bbox_noncontour_as_background`, `bbox_noncontour_region`) from a single model forward per H5 (S5-12, Step E7). Optional `--export_ply_alias`/`--ply_output_dir` writes GT/prediction diagnostic PLYs (Step E8).
- `checks/dummy/check_dummy_class_weight_tag.sh`: synthetic test of `train_stage5.sh`'s `class_weight_tag()` run-naming function (auto/manual/none -> filesystem-safe tag), extracting the function body directly from `train_stage5.sh` via `sed` so it cannot silently drift from the real implementation (S5-13, Step F3). Bash-only, no Python/CUDA needed.

When `check_stage5_s5_15_p1_manifest_audit.py` is brought back into use, two further set-dependent
values need updating in the same way as `EXPECTED_INPUT_FILES`: its `--expected_train_files`
(default 162, which becomes 144) and `--expected_val_files`.

When artifact coverage records are built, the intended method is that **the producer of an artifact
records its input contract and target set at generation time**. Registering an existing artifact
requires verifying its provenance first; reading an artifact's contents and then declaring it safe is
the order this is meant to avoid.
