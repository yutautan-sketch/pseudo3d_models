## 3. 確認した事実

### 3.1 [`mk_legcase_json.py`](../../../research/stage5/s5-16/step0/reference_scripts/mk_legcase_json.py)が計算している値

実装チャットで同スクリプト（365行）を読み、`femur_traj_len`の算出内容を確認した。

1. 各frameで`leg` BBoxを切り出し、median blur背景差分 → CLAHE → Otsu二値化を行い、
   **最大輪郭の重心**を求める（輪郭が取れない場合はBBox中心へフォールバック）。
2. 重心を`(x / width, y / height)`で正規化し、最近傍かつ時系列単調の制約でtrackへ連結する。
3. **連続frame間のユークリッド距離を積算**した軌跡長が`femur_traj_len`。

つまりこの値は、大腿骨の解剖学的長さではなく、
**sweep中に大腿骨断面の重心が画像平面上を移動した軌跡長**である。留意点は次のとおり。

- **単位は正規化座標**であり、xはwidth、yはheightという**異なる分母**で割られている。
  等方的な距離ではなく、mmでもない。
- **画像平面内の移動のみ**を積算しており、pseudo-3Dのtrackingが持つ面外方向の運動を含まない。
- track範囲は`start`/`end`という**別系統のXMLアノテーション**（`femur_end_anno`）に依存する。
- スクリプト内のパスは別データセット（`251117_検証用`）を指しており、
  現在の180動画を覆うかは未確認。

### 3.2 teacher v7 H5には端点情報が無い

`train_stage5.sh`のteacher preflightが要求する必須datasetを確認した。

```
point_cloud/frame_order, annotation/point_label, annotation/valid_mask,
frame_annotation/frame_order, manual_review_fullvideo_frames/*,
xml_annotation_invalidation/*, crop_quality_invalidation/*
```

[`mk_legcase_json.py`](../../../research/stage5/s5-16/step0/reference_scripts/mk_legcase_json.py)が使う`start`/`end`マーカーに相当するものは**含まれていない**。
Stage 5のH5が持つのは点単位ラベル（0/1/-1）とBBox由来のignore領域である。

### 3.3 mmスケールについて

動画ごとの可変性は既存実装で対応済みである（`audit_stage5_train_core_mm_metadata.py`は
動画ごとに、x/yを個別に読み取る）。

**残る未確認事項:** mm/pixelが**元frame基準か、crop/resize後基準か**。
`pixel_xy`はlocal crop座標系であるため、元frame基準なら`local_resize_scale`・
`local_crop_left/top`の逆変換を挟む必要がある。S5-16 10.0の換算経路
（`pixel_xy`→crop逆変換→元frame→mm）はこの前提で書かれており、確認が要る。

## 4. Step 0の範囲外だが提起が必要な2件

### 4.1 S5-17の仮説H17-1が循環になる可能性

H17-1は「GTから導くどの幾何表現・代理FL定義が、臨床FLと最もよく一致するか」であり、
採否規則は「train_coreで臨床FLとの誤差が最小のものを事前規則で1つ選んで固定する」である。

参照側のFLがGTアノテーション由来であるなら、
**この比較は同一ラベルの2通りの導出同士の比較になり、臨床的な正しさを示すものにはならない**（［推論］）。
選ばれるのは「既存のアノテーション処理系列に最も近い代理FL定義」である。
診断として無意味ではないが、H17-1が意図した「臨床値との一致の確認」とは異なる。

**S5-17実装依頼書の作成前に、H17-1の目的と採否規則を見直す必要がある。**
Step 0の判断とは独立であり、本書では解決しない。

### 4.2 A案（外部test）の参照値の妥当性留保

真に独立した実測FLは未アノテーション動画側にのみ存在する。
ユーザーは「実測値は動画取得とは別に測定されており、動画に映る大腿骨の長さと異なる可能性がある」と
申告している。S5-16 9.2はA案を「臨床FLを参照値とするend-to-end FL test」としているため、
**A案の設計時に持ち越すべき留保として記録しておく必要がある。**

これも本書では解決しない。なお、この留保を実際に確かめられるかどうかは、
実測FL付きデータへアノテーションを付けるかどうかに依存する。その可否を6章で判断依頼とする。

### 4.3 「データセットから導出する」案のStep 0での扱い

ユーザー提案（2章の3）について、Step 0の範囲で実施できるかを検討した。
**実装チャットの判断は「Step 0では実施すべきでない」である。** 理由は2点。

1. **teacher v7 H5に端点情報が無い**（3.2）。[`mk_legcase_json.py`](../../../research/stage5/s5-16/step0/reference_scripts/mk_legcase_json.py)と同じ導出はそのままでは行えない。
2. **マスクから端点を定義して代理FLを作る作業は、S5-17そのものである。**
   S5-16 10.1が「(a)軸平行BBox／(b)oriented box／(c)端点／(d)最良frameの端点／(e)pseudo-3D軸
   を比較し、事前規則で1つを選んで固定する」と定めた対象であり、
   Step 0依頼書6章は「ここでは代理FLを計算・選択せず、`T_FL`も推定しない」と明記している。
   Step 0で1案を実装すれば、S5-17の比較対象を先に既成事実化することになる。

ただしこの提案は、S5-17の実施方法としては有力である。**S5-17実装依頼書へ引き継ぐことを推奨する。**

## 5. 判断依頼1: Step 0の層化の第2軸（Step 0の進行を止めている）

D-037・9.2は層化の第2軸を「臨床FLの三分位」としているが、3章によりこの名称と前提が成立しない。
**実装は未着手であり、いずれの案を採っても実データの処理量は増えない。**

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 既存の`femur_traj_len`等を159件分の表として用意し、現行仕様のまま層化する | 表の作成コストが残る。「臨床FL」の名称を改める必要がある。180動画を覆うかも未確認 |
| **B（推奨）** | 層化の第2軸を、split構築処理内でGTから直接算出する**層化専用のサイズ代理量**に置き換える（例: GT陽性frame数、主軸方向のGT広がり）。**代理FL定義ではないこと、S5-17へ引き継がないことを仕様へ明記する** | 表が不要。追加I/Oなし（builderは既にGT点を読む）。S5-17の選定を先取りしない。層化の目的は保たれる |

### 5.1 B案を推奨する理由

- 層化の目的は「大きさ・範囲の偏りを分割間で抑える」ことであり、その目的にはGT由来の代理量で足りる。
  **臨床的な正しさが要求されるのはS5-17以降の評価であって、split構築時の層化ではない。**
- 臨床値を一切読まないため、9.2で設計した「FL周辺度数をsplit確定前に1回だけ共有する」手続きが不要になる。
  11.7.2で「候補GT統計の共有出力は認めない」とされているため、
  **工程2aの共有出力は「層が構成可能か」の真偽と候補件数のみ**となる。漏洩面ではより安全である。
- 表の準備を待たずにStep 0を進められる。現在この1点で工程2aが停止している。

## 6. 判断依頼2: 実測FL付きデータのアノテーション作成（Step 0は止めない）

ユーザー回答（2章の5）: アノテーション作成は可能だが時間がかかる。実測FLを持つデータは**数例**のみ。
それでも意味があるなら、S5-18・S5-19の学習のタイミングで進めたい。

### 6.1 既存方針との整合

S5-16 11.5は「A案の準備: 未使用動画のpseudo-3D生成と臨床FLの紐付けは、S5-17〜S5-20と並行して
進めてよい。ただし、方式選択には一切使わない」としている。
**S5-18・S5-19と並行して進めること自体は、既存方針の範囲内である。**
GPU学習中の人手・CPU作業であり、実施量の競合も小さい。

### 6.2 数例で何ができないか

- **S5-16 9.2がA案に期待する「end-to-end FL test」としての統計的評価はできない。**
  10.4の採否規則（動画単位FL誤差のMAE、失敗率、動画別で過半が改善、prior-onlyを明確に上回る）は
  数例では判定できない。**数例の結果をproduction判断やtask採否の根拠にしてはならない。**
- A案の完成を意味しない。9.2のA案は引き続き、教師contourが付与された十分な件数の未使用動画を要する。

### 6.3 数例でもできる可能性があること（価値が高い順）

1. **導出FLと実測FLのペア比較。** 新データにアノテーションが付けば、**同一動画について
   「アノテーション由来FL」と「実測FL」の両方**が得られる。この対応は現在どこにも存在しない。
   数例でも「導出FLが実測からどの程度ずれるか」の目安になり、
   **4.1で指摘した循環性に対する唯一の外部的な足がかりになる**（［推論］）。
   件数が0から数例へ増えることは、100から110へ増えることとは質的に異なる。
2. **mm換算チェーンの端から端までの検証。** `pixel_xy`→crop逆変換→元frame→mmの経路が、
   独立した実測値に対して桁・オーダーで整合するか。性能評価ではなく実装の健全性確認であり、
   数例で足りる。3.3の未確認事項（mm/pixelの基準）の検証にも使える。
3. 教師contourが付けば、幾何表現・segmentationの定性確認。

### 6.4 前提となる制約（解けないと6.3の1も2も解釈できない）

ユーザー申告のとおり、実測は動画取得とは別に行われており、動画に映る大腿骨長と一致しない可能性がある。
**不一致が出た場合に「パイプラインが誤っている」のか「参照値が動画に対応していない」のかを
区別できない。** この曖昧さが残るかぎり、アノテーションを増やしても解釈可能な結論は得られない。

したがって、**アノテーション作成に着手する前に、実測値と動画の対応可能性を先に確認する**ことを推奨する。
確認項目: 測定時期と動画取得時期の差、測定部位・手技、同一被検者・同一検査に紐づくか、
複数回測定の有無、左右の別。人手で確認でき、低コストである。

### 6.5 推奨

**条件付きで実施を推奨する。**

1. 先に6.4の対応可能性を確認する（アノテーション作業を伴わない）。
2. 対応が確認できた場合に限り、S5-18・S5-19と並行してアノテーションを作成する。
3. 用途を**「A案のend-to-end test」ではなく「導出FLの実測に対する較正と、mm換算チェーンの検証」**
   として位置づけ、数例であることを記録に明記し、採否判断には使わない。
4. 対応が確認できない場合は着手しない。その事実自体を、A案の参照値に関する留保（4.2）として記録する。

### 6.6 判断が必要な点

| # | 事項 |
| --- | --- |
| a | 実施するか |
| b | 用途を6.5-3の限定（較正とチェーン検証、採否判断に使わない）としてよいか |
| c | 6.4の対応可能性確認を着手条件とするか |
| d | 着手時期（S5-18開始時／S5-19／それ以前） |

本件はStep 0の進行を妨げない。**S5-18開始前までに決まればよい。**

#### 9.2.2 層化量の意味と目的を明確にする

5章の「GT由来の代理量で大きさ・範囲の偏りを抑えられる」「層化の目的は保たれる」という説明は、
採用する量の意味と限界を確定する前の断定になっている。名称はまず「GT由来の層化専用量」とし、
何の偏りを抑えるかを明記する。「サイズ代理量」「FL相当量」とは現時点で呼ばない。

| 候補 | 表すもの | 定義時に必要な注意点 |
| --- | --- | --- |
| GT陽性frame数 | GT陽性点が観測されたframeの数 | 動画長・frame抽出条件・点サンプリングに依存する。骨の大きさとは限らない |
| GT陽性frame率 | 定義した対象frame集合におけるGT陽性frameの割合 | 動画長の影響を一部抑えられるが、分母を固定する必要がある。骨の大きさではなく観測割合である |
| GTの主軸方向の広がり | 定義した座標系・点集合における空間的範囲 | crop/resize、座標軸の単位、複数領域、外れ点、frame間移動、動画単位への集約方法に依存する |

コード確認では、`Stage5/checks/real_h5/check_stage5_gt_component_count.py` の `read_gt_points` は、
`point_cloud/pixel_xy`・`frame_order`とラベル・valid maskを読み、
`valid_mask & (point_label == 1)`をGT陽性点としている。
`analyze_video` の `num_gt_frames` は、そのGT陽性点が存在する一意なframe数である。
**元の教師マスク全体の面積や広がりを直接計測しているわけではない。**

したがって、時間方向の観測範囲を揃えるのか、空間的な大きさを揃えるのかを先に決める。
前者を採る場合は、臨床FLに基づく大きさの均衡という旧目的からの変更を明記する。
後者を採る場合は、座標変換・領域選択・集約まで含めた算出仕様を提示する。
GT陽性frame率の分母に、GT陽性frameだけを使ってはならない。対象frame集合、ignoreのみのframe、
有効点のないframe、H5内に点がないframeの扱いを定め、必要な入力から識別可能か確認する。

#### 9.2.3 元frame基準のmmスケールの適用範囲

9.1のユーザー回答を、層化量の種類に応じて次のように適用する。

- frame数・frame率を採用する場合は、層化量の算出にmm換算を要求しない。
- 空間的な広がりを物理量として比較する場合は、crop/resizeを逆変換して元frame座標へ戻し、
  動画に対応する元frame基準のmm/pixelを適用する。値の取得と対応関係の検証は別途必要である。
- 元frameのx/yのmm/pixelが判明しただけでは、frame間方向を含むpseudo-3D全体の主軸長を

- frame内の広がりを採る場合も、対象領域と、frameごとの値を動画単位に集約する方法を固定する。

今回のB案採用は、Step 0に未確定の3D長さ定義を導入する決定ではない。

#### 9.2.4 算出仕様・三分割・停止条件の強化

算出式、入力、対象frame、有効点条件、領域の扱い、動画単位の集約方法は、
**候補159件の結果を見る前に固定する。** 候補GTの分布を見ながら都合のよい指標を選び直さない。
仕様不備が判明した場合は停止して管理チャットへ報告し、変更理由と版を残して再判断する。

| 項目 | 必要な仕様・確認 |
| --- | --- |
| 正常なゼロ | 算出定義上有効なゼロと、入力欠損・不正値・算出不能を区別する。ゼロを一律に欠損扱いしない |
| 入力・値の検査 | 必須フィールド、配列の対応、frame識別子、算出に必要な有効データ、有限値、許容範囲を検査する。異常を黙ってゼロや欠損層に置換しない |
| 分母・空集合 | frame率の分母ゼロ、空のGT集合、空間量を定義できない点集合などの扱いを明示する |
| 三分割の意味 | 全件同値など、順位上は分割できても層化量に差が生じない場合の停止・再判断条件を定める |
| 同値 | 現行の旧リスト順による同値処理を維持する場合、その仕様と限界を記録する。境界の同値が複数群へ分かれ得ることを隠さない |
| 抽出 | 三分割・最大剰余配分・seed 42・SHA-256鍵付き抽出・既存の分割契約を維持し、方法を記録する |
| 保証範囲 | 小さい層から必ず選出されることや、分割後の分布が完全に一致することは保証しない |

`Stage5/stage5/utils/split_allocation.py` の現行 `assign_fl_groups` は、
値と旧リスト順で整列して所定件数へ分ける。このため同値ばかりでも形式的な三分割はできる。

層化量の定義と合わせて提示・確定する。算出不能を理由にC案へ自動変更することも認めない。
